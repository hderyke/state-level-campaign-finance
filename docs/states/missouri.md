# Missouri — Pipeline Documentation

---

## Overview

| | |
|---|---|
| **State** | Missouri (MO) |
| **Source** | [Missouri Ethics Commission (MEC) Campaign Finance Search](https://mec.mo.gov/mec/Campaign_Finance/CFSearch.aspx) |
| **Access method** | Playwright browser automation against an ASP.NET WebForms UI — no API, no bulk per-state export |
| **Coverage** | Committee registry: all registered committees, Active + Terminated. Transactions: swept statewide by (date range × amount range) per year, not per-committee — see "Phase D was rearchitected" below — only as far back as swept via `--start-year` |
| **person_id model** | `person` — a candidate committee's MECID persists across election cycles *and* across different offices; `person_id` set directly from it |

**Must run locally, not from a cloud host.** MEC sits behind an Incapsula/Imperva WAF that blocks datacenter/cloud IPs outright — confirmed both via raw `curl` (WAF challenge page) and headless Playwright (`net::ERR_CONNECTION_RESET`) from a cloud sandbox. Same constraint as Alaska; run via `headless=False` on a real machine.

## Raw Data Structure

`data/Missouri/raw/`

### committees_active.xls / committees_terminated.xls

CFSearch.aspx's "Committee Type" tab, Committee Type = Select All, Committee Status = Active / Terminated respectively (Select-All + Select-All is rejected by the site — "Please Limit the search by Committee Type or Status" — so it's split into these two searches, which together cover every Committee Type in two requests instead of ~10 individual-type searches).

Despite the `.xls` extension, these are HTML tables (openable with `pandas.read_html` or BeautifulSoup — the scraper/parser use the latter to avoid adding a pandas dependency).

| Field | Description |
|---|---|
| `MECID` | Missouri Ethics Commission ID — primary key throughout |
| `Committee` | Committee name |
| `Candidate` | Candidate name (candidate committees only) |
| `Treasurer` | Treasurer name |
| `Deputy Treasurer` | Deputy treasurer name, if any |
| `Committee Type` | e.g. "Candidate", "Political Action/Continuing", "Political Party" |
| `Committee Status` | "Active", "Terminated", "Terminated (Suspended)" |

Confirmed against a real export: 13,431 rows, `Committee Status` breakdown `Terminated 11,572 / Active 1,833 / Terminated (Suspended) 26`.

### committee_detail.csv

One row per MECID from `CommInfo.aspx?MECID={mecid}` (plain GET). This is the **only** source for `party` — it does not appear anywhere in the bulk committee list. Also the source for committee/candidate/treasurer addresses (parsed from an ASP.NET `<span>` where the street and city/state/zip lines are joined by `<br>` with no space — the scraper splits on the raw `<br>` tags rather than guessing from concatenated text).

| Field | Description |
|---|---|
| `mecid` | MECID |
| `committee_name`, `committee_status`, `committee_type`, `term_date` | Committee-level fields |
| `address`, `city`, `state`, `zip`, `phone` | Committee mailing address |
| `candidate_name`, `cand_address`, `cand_city`, `cand_state`, `cand_zip`, `cand_phone` | Candidate fields — blank for non-candidate committees |
| `party` | Candidate's party — **only source for this field** |
| `treasurer_name`, `tre_address`, `tre_city`, `tre_state`, `tre_zip`, `tre_phone` | Treasurer fields |

### election_history.csv

One row per (committee, election) the committee's candidate has run in — from the same `CommInfo.aspx` page's Election History gridview (`gvElecHistory`). Empty for non-candidate committees (PACs never populate this grid).

| Field | Description |
|---|---|
| `mecid` | Joins to `committee_detail.csv` |
| `election_date` | e.g. "11/5/2024" |
| `election_type` | "Primary Election" / "General Election" |
| `office` | e.g. "Governor" |
| `district` | Blank for statewide offices, e.g. "6" for a State Senate seat |
| `political_subdivision` | Fuller text, e.g. "Office of the Governor" |

Confirmed on Mike Kehoe's committee (MECID `C091155`): the *same* MECID has election-history rows spanning State Senate District 6 (2010, 2014), Lieutenant Governor (2020), and Governor (2024, 2028) — i.e. Missouri candidate committees are not re-registered each cycle or each office, unlike states such as Alabama/Arizona/California. This directly drove the `person` id_model choice (see Parser section).

### contributions/{mecid}_{year}.xls

`CF12_ContrExpend.aspx`, Contributor tab → Advanced Search sub-tab, Committee ID + Year filters, "Export Results to Excel". Confirmed against a real 2,801-row export:

| Field | Description |
|---|---|
| `MECID`, `Committee` | Filing committee |
| `Report` | Free-text report name the transaction was filed under, e.g. "April Quarterly Report", "AMENDED 30 Day After Primary Election-8/6/2024" |
| `Contributor-Committee` | Populated when the contribution is a transfer from another committee |
| `Contributor-Company` | Populated for business/organization contributors |
| `Contributor-Last Name` / `Contributor-First Name` | Populated for individual contributors |
| `Address1`, `Address2`, `City`, `State`, `Zip` | Contributor address (`Address2` was empty across the whole sample) |
| `Employer`, `Occupation` | Individual contributor fields |
| `Contribution Date`, `Contribution Amount` | `MM/DD/YYYY`, `"$1,234.56"` |
| `Monetary/In-Kind` | Contribution form |
| `Committee` *(again)* | A **second** column also named "Committee" — the transfer flag ("Yes"/"No"). MEC's raw HTML genuinely repeats the header; the scraper's `_dedupe_headers` renames it `Committee.1`, matching `pandas.read_html`'s own convention for duplicate headers. |

Non-null counts from the sample: `Contributor-Committee` 146/2801, `Contributor-Company` 42/2801, `Contributor-Last Name`/`Contributor-First Name` ~2613/2801, `Employer`/`Occupation` ~2609–2613/2801. Transfer flag (`Committee.1`): 146 "Yes", 2655 "No".

### expenditures/{mecid}_{year}.xls

Same page, Expenditure tab → Advanced Search. Mirrors the contribution export but for payees; no transfer-flag column (expenditures don't have the equivalent duplicate-header issue). This is a committee's **own ordinary spending** — payroll, ads, consulting, vendors — and carries no field indicating which candidate (if any) it supports or opposes. Not to be confused with independent expenditures, below.

| Field | Description |
|---|---|
| `MECID`, `Committee Name`, `Report` | Filing committee |
| `Expenditure-Last Name` / `Expenditure-First Name` / `Expenditure-Company` | Payee identity |
| `Expenditure-Address1`, `Expenditure-Address2`, `Expenditure-City`, `Expenditure-State`, `Expenditure-Zip` | Payee address |
| `Expenditure Purpose` | Free-text purpose |
| `Expenditure Date`, `Expenditure Amount` | `MM/DD/YYYY`, `"$1,234.56"` |
| `Expenditure Type` | "Paid" or "Incurred" — a payment-status flag, not an in-kind/monetary distinction |

### independent_expenditures_{year}.xls

`CF_SearchDirExp.aspx` — "Committee Expenditures for Candidates" search. This is MEC's actual **independent expenditure** report: money a committee spends directly to a vendor to support or oppose a specific candidate, **without** that candidate's coordination or consultation — structurally distinct from the ordinary per-committee `expenditures/{mecid}_{year}.xls` export above, which has no supported/opposed-candidate field at all.

Unlike every other transaction export on this site, this one is a genuine **statewide bulk export**: Committee ID is not a filter on this form (Report Year is the only required field), so it's swept once per year rather than once per committee per year. Confirmed against a real export: 1,718 records for report year 2026 alone.

| Field | Description |
|---|---|
| `Candidates Name and Address` | A single concatenated string — candidate name, then street, then city/state/zip, with no reliable delimiter between them (e.g. `"JT Holman 1103 E BRIGGS DR   Macon MO 63552"`). The parser extracts just the name (see Parser section) — there's no schema column for the candidate's address anyway. |
| `Office Sought` | e.g. "Mayor", "Presiding Commissioner" |
| `Support/Oppose` | "Support" or "Oppose" — always one of these two on an actual row; "All" is only a search filter, never a data value |
| `Date`, `Amount` | `MM/DD/YYYY`, `"$1,234.56"` |
| `Reporting Committee` | The committee that made the expenditure. Plain text only — MEC renders this as a postback link in the UI (`javascript:__doPostBack(...)`), so no MECID is recoverable from the exported HTML |
| `Report` | Free-text report name, same convention as the other exports |

There is no vendor/payee field on this report at all — MEC discloses who the expenditure targets (the candidate) and who made it (the reporting committee), but not who was paid.

## Scraper

`src/pipeline/scrapers/missouri.py`

Five phases, all Playwright-driven:

**Phase A — committee registry.** Two searches (Status=Active, Status=Terminated) on CFSearch.aspx's Committee Type tab, each exported to Excel.

**Phase B — per-committee detail sweep.** For every MECID discovered in Phase A, `goto()` `CommInfo.aspx?MECID={mecid}` directly (plain GET, no form interaction) and parse the ASP.NET `<span id="...lblXxx">` fields plus the `gvElecHistory` gridview. This is a full sweep of every registered committee (~13,000+ as of this writing) — expect several hours. Resumable via `manifest.csv` keyed by MECID; safe to `Ctrl-C` and re-run. Retries up to 4 times per page (with backoff) if a bot/CAPTCHA-style interstitial is suspected — see the "Bot-block retries" note below.

**Phase D — statewide transactions, swept by (date range × amount range), not per-committee.** Fills the Advanced Search form (`Year`, `From`/`To` date, `Starting at`/`Ending at` amount — **`Committee ID` left blank**) and clicks Search. **Critical gotcha, found via hours of interactive testing:** the results open in a genuine popup (`window.open`), but only from an onload handler that fires *after* the search's full-page postback completes — so the click's user-activation doesn't carry over the navigation, and Chromium's popup blocker silently swallows the `window.open()` with no error and no popup. The fix is launching Chromium with `args=["--disable-popup-blocking"]`; there is no equivalent of "allow popups for this site" available to a throwaway Playwright profile. Once the popup is open, "Export Results to Excel" is a normal file download.

**Phase D was rearchitected from per-(committee, year) to statewide (date × amount) chunks — the original "Committee ID is required" premise was wrong.** The scraper originally looped every MECID × year (~40,000+ searches across ~20,000 committees), on the strength of an earlier test showing that leaving every Advanced Search field blank except Year returned nothing. That test only tried Year alone — it never tried Year **plus a date range** with Committee ID still blank. Confirmed live via direct interactive testing that a Year + From/To date range, with Committee ID and every other field left blank, returns a genuine statewide, cross-committee result set — 9,436 contribution rows for just January 2026 alone, spanning dozens of different MECIDs, each row carrying its own `MECID`/`Committee Name` column. The per-committee loop was also quietly the root cause of most of the export failures that had looked committee-specific: a real production run showed the same "export download failed → MEC server error" failure hitting most committees in sequence, not just the one (A101029) that had been confirmed to have a genuine, reproducible MEC-side bug. Switching to statewide chunks cuts total searches from ~40,000 to a few hundred per year (see chunking below) and removes the per-committee loop entirely.

**The true root cause of most export failures: a bare HTTP 503 on the export POST itself, unrelated to result-set size.** Direct testing (capturing the actual network response, not just DOM/URL state) confirmed the "Export Results to Excel" click is a plain form POST back to `CF12_ContrExpendResults.aspx`, and that POST returned a **503 Service Unavailable — on the exact same URL, no redirect to `Error.aspx`** — for two very differently-sized result sets tested back to back: a 9,436-row statewide month, and a 396-row single day. Since a modest, previously-safe-looking size still 503'd, this is not a "your query is too big" signal at all — it's HTTP's standard "the server is temporarily unable to handle this, try again" status. This is a **different failure signature** from the already-documented `Error.aspx` app-level bug (which redirects to a different URL and is confirmed non-transient) — `_mec_server_error`'s URL check never catches a same-URL 503, so this failure mode had been silently falling through to the generic "dropped download, retry blindly" path, which just burned the full timeout every time without ever recognizing what was actually happening. **Fixed** by reading the export click's response directly via Playwright's `Response` object (`_click_export`, capturing status + body via `popup.expect_response(...)` rather than the separate download-event API) so an HTTP 5xx is detected the moment the POST comes back (a couple seconds) instead of after a long download-wait timeout, and is retried with backoff (`MAX_EXPORT_HTTP_ERROR_RETRIES` = 4) since 503 is exactly the case HTTP retry semantics exist for — distinct from the genuine `Error.aspx` bug, which still isn't retried. Reading `response.body()` directly also means a successful export no longer depends on Chromium's separate download-event machinery firing correctly at all; the response body **is** the `.xls` content.

**Chunking design (`_process_date_amount_chunk`).** Each year × relation_type is partitioned into `DATE_CHUNK_DAYS` (14-day) windows × `AMOUNT_TIER_BOUNDS` (`[0, 100, 500, 1_000, 5_000, 25_000, 10_000_000]`, chosen unevenly since real contribution/expenditure amounts skew heavily toward small dollar figures) — 162 chunks/year/relation_type by construction (verified: exactly 365 days covered per tier, contiguous, no gaps or overlaps). Adjacent chunks share a boundary amount (e.g. tiers `[0,100)` and `[100,500)` both touch $100) — since "Ending at" is assumed inclusive (not separately confirmed), the code fills `txtEndAmt` with the boundary minus one cent so a transaction landing exactly on a round-number boundary isn't double-counted, while `amt_hi` itself stays the clean round number everywhere else (filenames, logs, split math). Each chunk is checked for size **before** attempting export (via the on-screen "Full Disclosure Reports (N)" count) and split further — date axis first, then amount axis — if `N > SAFE_EXPORT_ROW_THRESHOLD` (500, a conservative guess: a 478-row single-committee export was previously confirmed reliable, a 9,436-row statewide month was not). Splitting **also** triggers reactively if an export fails anyway even after its own retries (confirmed necessary: a 503 hit a modest 396-row chunk too, so size alone isn't a reliable predictor), up to `MAX_CHUNK_SPLIT_DEPTH` (6, i.e. up to 64x narrower than the initial chunk) before giving up and reporting that leaf as `"blocked"`.

**Manifest/resumability changed to top-level-chunk granularity.** A top-level (year, 14-day window, amount tier) chunk may fan out into many smaller leaves via adaptive splitting, but that's invisible to the manifest — only whether the *entire* top-level chunk fully succeeded (every leaf `"ok"`/`"empty"`, none `"blocked"`) gets recorded as done. A partial failure leaves the whole top-level chunk unmarked, so a future re-run retries it in full — re-downloading already-succeeded sub-chunks is wasted work but harmless (same filename, same content, idempotent overwrite). Retries up to `PAGE_RETRY_TRIES` (4) times per search if the results popup fails to open, or opens but looks like a bot/CAPTCHA screen rather than a genuinely empty result set.

**Not yet independently re-verified end-to-end: a real, successful statewide export under this new code.** Live testing that established the above (blank-Committee-ID search working, the 503 root cause, chunk sizing) happened while MEC's export endpoint appeared to be having a genuine, current outage or instability — every export attempt during that testing session hit the 503, regardless of size, including immediate back-to-back retries. That's strong evidence the 503 itself is a real, transient MEC-side condition rather than anything caused by query shape — but it also means the first real production run of this rearchitected Phase D is the actual end-to-end test of the new `_click_export`/`_export_from_popup` path (response-body-based file saving in particular) succeeding on real data, not just failing fast and correctly. Worth double-checking the very first successful `.xls` file this produces opens correctly and has the expected columns (see "MECID/committee_name now read per-row" below) before trusting a long unattended run.

**`response.body()`-based export saving (described above) doesn't actually work for real Chromium downloads — reverted to `expect_download()`.** The prediction in the paragraph above ("the first real production run... is the actual end-to-end test") came true and failed: a full production run showed **100% of export attempts failing** with "export download didn't complete"/no response received, all the way down to single-day, $25-wide chunks that should have had almost no data — while the user directly observed real files completing their downloads in the browser at the same time. That observation falsified the size/committee-specific theory and pointed straight at the export-saving mechanism itself. Root cause: once Chromium classifies a navigation as a file download (via the `Content-Disposition` header on the export POST's response), it hands that response off to the browser's native download manager *before* Playwright's ordinary `Response.body()`-reading machinery gets a usable copy — so `popup.expect_response(...)` + `.body()` can see the response's status/headers just fine but reads back an empty/unusable body for the actual download case, even though it appeared to work in earlier isolated manual testing (which wasn't triggering a real download the same way `popup.click()` does). This is exactly why Playwright ships a separate `page.on("download")`/`expect_download()` API in the first place, rather than expecting callers to read download responses like ordinary ones. **Fixed** by reverting `_click_export` to use `popup.expect_download()` as the primary/proven mechanism — this is what actually saved real files earlier in this project's testing (A101165, A121061) — while keeping a lightweight, non-blocking `popup.on("response", ...)` listener purely to still get fast HTTP-5xx diagnosis (status/headers ARE reliably readable even when the body isn't) without needing to read the download's own body. This **supersedes** the "reading `response.body()` directly" description in the 503 paragraph above — that mechanism is what the code was originally changed to, but it never worked for real downloads in production. Also fixed: the "timeout" case (no download, nothing diagnosable) previously discarded its actual exception text and logged a generic "no response received" message — now logs the real underlying error, since the silent discarding was part of why this bug took a full production run to catch instead of being obvious from the logs.

**Confirmed end-to-end after the `expect_download()` fix: real statewide bulk chunk files download, parse, and validate correctly.** A subsequent production run produced genuine multi-hundred-row chunk files (e.g. `2026_01012026-01042026_0-100.xls`, 369 rows; `2026_01132026-01132026_0-100.xls`, 412 rows) that the parser read with zero column-mismatch issues, taking contributions.csv.gz from 9 rows (old per-committee-only data) to 3,381 rows in one partial run. `validate.py` passed Tier 1 at 100% across the board. This closes out the "not yet independently re-verified" caveat above — the new `_click_export`/`_export_from_popup` path is confirmed working on real data, not just failing fast and correctly. One residual pattern worth noting: the very first attempt of that run still saw a short burst of total failure (4 chunks in a row failed export even split all the way down to a single day and a $25-wide amount band), while a fresh restart moments later succeeded immediately on that exact same chunk at its original (unsplit) size — consistent with a brief transient MEC-side outage rather than anything size- or query-shape-related, and handled gracefully by the existing split/retry/`"blocked"` design (a stuck leaf eventually gives up and lets the rest of the sweep continue, rather than hanging or crashing the run).

**MECID/committee_name/election_year now read per-row from the exported table, not from the filename.** The old per-committee export's filename (`{mecid}_{year}.xls`) was the only place `mecid`/`election_year` came from for some rows; the parser already had a `row.get("MECID", "") or mecid_from_name` fallback (apparently anticipating this exact change), so no parser change was needed there. `election_year` did need a change — it was purely filename-derived (`{mecid}_{year}.xls`'s trailing year) — now derived from each row's own `Contribution Date`/`Expenditure Date` via `year_from_date()`, falling back to a filename-derived year only if that's blank. New filenames are `{year}_{fromISO}-{toISO}_{amtlo}-{amthi}.xls` (e.g. `2026_20260101-20260114_0-100.xls`); the old `^(.+)_(\d{4})\.xls$` regex doesn't match this shape, which is fine since it's now only a fallback. **Not independently re-verified:** the exact column set on a bulk, blank-Committee-ID export — confirmed live that `MECID` is a genuine leading column and the rest of the row content (contributor name/address, employer/occupation, date, amount, monetary/in-kind) visually matches the established per-committee export's fields, but the live testing that confirmed this was interrupted by the 503 outage before a real file could be downloaded and its exact column headers inspected directly. If parsed row counts look unexpectedly low on the first real run, check the actual downloaded `.xls`'s header row against what `src/pipeline/parsers/missouri.py`'s contributions/expenditures loops expect (`Committee`, `Committee.1`, `Contributor-Company`, `Contributor-Last Name`, `Contributor-First Name`, `City`, `State`, `Zip`, `Employer`, `Occupation`, `Report`, etc.).

**Phase E — independent expenditures.** `CF_SearchDirExp.aspx`'s "Committee Expenditures for Candidates" search — MEC's actual independent-expenditure report (committee spending FOR/AGAINST a candidate, not the committee's own ordinary spending covered by Phase D). Unlike Phase D, Committee ID is **not** required here — Report Year is the only required filter — so this is swept once per year, statewide, same shape as Phase A rather than Phase D. Same "Export Results to Excel" → HTML-table-as-.xls convention as everywhere else on this site.

**Phase E hit the same "redundant no-op postback" bug class as `lbtnContr` (above), on `ddYear` this time.** After Phase D's full 324-chunk sweep completed cleanly end-to-end (confirming the `expect_download()`/persistent-profile fixes above), Phase E failed 100% of the time with `Page.wait_for_function: Timeout 30000ms exceeded` on every one of its 4 attempts. Confirmed live via direct inspection of `CF_SearchDirExp.aspx`: its `ddYear` dropdown **defaults to the current calendar year already selected** on a fresh page load — and the scraper's default (no `--start-year`/`--end-year`) sweep target is also the current year, so `_select_year_and_postback` was setting `ddYear` to a value it already had. Just like the `lbtnContr` case, a no-op selection change doesn't regenerate `__VIEWSTATE`, so `_wait_for_postback`'s poll burned the entire 30s timeout — and since every retry reloads a fresh page (same default state every time), this wasn't a transient block a reload could ever clear; it would fail identically forever for the current year. **Fixed** by having `_select_year_and_postback` check the select's current value first and skip the postback entirely when it already matches the requested year — same fix shape as `lbtnContr`, just generalized to any `_select_year_and_postback` caller (both Phase D's `_search_cf12` and Phase E's `download_independent_expenditures` share this helper). Confirmed this doesn't affect Phase D: its `ddYear` apparently doesn't default to the current year the same way `CF_SearchDirExp.aspx`'s does, since the full 324-chunk contributions/expenditures sweep already completed successfully before this fix existed — the guard is a no-op there and only changes behavior on pages where the value truly doesn't need to change.

**Phase E's Search button needed the same VIEWSTATE-diff treatment as everything else, even though it's a genuine `<input type="submit">`, not a JS postback link.** During a `--start-year` historical backfill, Phase E started needing a human to physically click Search in the visible browser before the sweep would proceed at all — even though the exact same click, replayed manually in a plain (non-Playwright) browser tab, returned real results in a few seconds. `btnSearch` was confirmed live via direct DOM inspection to have no `onclick` handler and a form `action`/`method` pointing at a same-URL POST, so on paper `page.click()` + `page.wait_for_load_state("load")` should have been fine — but same-URL POSTs are the exact weak spot documented above for `expect_navigation()`, and it turns out `wait_for_load_state` inherits the same blind spot. **Fixed** by wrapping `page.click(f"#{P}btnSearch")` in `_wait_for_postback` (the shared VIEWSTATE-diff poller) instead of trusting `wait_for_load_state` to notice the click landed, with the timeout kept at 120s since a genuinely slow-but-real statewide export is plausible here. **This fix alone did not resolve the reported symptom** — see the next entry.

**The actual stuck step was `ddYear`'s postback, not the Search button — a genuinely-synthetic JS trigger appears to get silently dropped after sustained automated traffic.** After deploying the Search-button fix above, a subsequent `--start-year` backfill still needed a manual intervention on year 2021 (after ~38 minutes/324 chunks of Phase D traffic immediately preceding it) — but the actual production log showed the failure was `Page.wait_for_function: Timeout 30000ms exceeded` inside `_select_year_and_postback`, a different step than the one just fixed. Confirmed directly with the user that the manual click was genuinely what unstuck the run, not a coincidental/preemptive click during an already-recovering retry — ruling out "just needs more time" as the explanation, since every retry already reloads a fresh page and re-attempts the same JS-only trigger from scratch. Leading theory: `_select_year_and_postback`'s original mechanism (`document.querySelector(sel).value = val; __doPostBack(target, '')`, called entirely via `page.evaluate()`) is about as synthetic an interaction as it gets — no real DOM event, no user gesture — and something in MEC's WAF/session layer appears to start silently discarding postbacks like this after sustained heavy automated traffic, while it still accepts postbacks that originate from genuine trusted interactions (consistent with the Search-button case just above, which is a real `page.click()` and never needed a manual assist). **Fixed** by switching `_select_year_and_postback`'s primary trigger to Playwright's native `page.select_option()`, which dispatches trusted `input`/`change` DOM events and lets the page's own `onchange` handler fire `__doPostBack` itself — still detected via `_wait_for_postback`'s VIEWSTATE poll rather than navigation events, so the original reason `select_option()` was avoided (unreliable `wait_for_load_state` timing) no longer applies. Falls back automatically to the original raw-JS trigger if `select_option()` itself fails (e.g. an actionability check failing because something overlaps the control, the same class of issue that ruled out physical clicks on the tab links) or if the postback still doesn't complete after a successful `select_option()` call — so Phase D's already-proven-reliable 324-chunk-sweep behavior can't regress even if this theory turns out wrong for some page/control. **Not yet independently confirmed end-to-end** — this is the second fix attempt for this symptom (the first, the Search-button fix above, did not resolve it), so it should be treated as a well-justified hypothesis pending a real backfill run past year 2021 without manual intervention, not a confirmed fix.

**Manifest:** `data/Missouri/manifest.csv`, keyed by `(relation_type, key)` — `key` is the Status string for `committees`, the MECID for `committee_detail`, `{year}_{fromISO}_{toISO}_{amtlo}-{amthi}` (a top-level date+amount chunk — see Phase D above) for `contributions`/`expenditures`, and the year for `independent_expenditures`. Pre-rearchitecture manifest rows for `contributions`/`expenditures` (old `{mecid}_{year}` keys) are simply never matched by the new key format going forward — they stay in the CSV for audit history but are functionally orphaned, not a problem since `upsert_manifest` only appends/updates.

**Vertical scope:** default (no flags) sweeps Phase D/E for the *current year only*; `--start-year`/`--end-year` requests a historical range; `--force` re-fetches everything in scope.

**Bot-block retries:** individual pages (Phase B's `CommInfo.aspx?MECID=X`, Phase D's per-committee-year search popup, Phase E's per-year search) occasionally serve a bot-block/CAPTCHA-style interstitial instead of the real page — confirmed to happen with wording other than the plain "Request Rejected" text `_goto_with_retry` checks for on the initial page load. Each of these three retries up to `PAGE_RETRY_TRIES` (4) times with backoff (`PAGE_RETRY_SLEEP * attempt`), using a generic phrase list (`BOT_BLOCK_PHRASES`) plus a structural fallback — if the expected content just isn't there after a reload, it retries regardless of what the block page actually says. A genuinely empty result (no data for that committee/year, no block-page phrasing) is still accepted immediately rather than retried.

**MEC server errors (distinct from bot-blocks):** confirmed live in production — for some specific committee/year combinations, `CF12_ContrExpendResults.aspx` redirects to MEC's own generic unhandled-exception page (`Error.aspx?aspxerrorpath=...`, e.g. "Error Message: Count cannot be less than zero. Parameter name: count"). This is a genuine bug on MEC's end, not a WAF/bot-block, and its wording doesn't match any `BOT_BLOCK_PHRASES` — without a dedicated check it would fall straight through to "empty" and get permanently recorded in the manifest as "done, 0 rows", silently masking real data forever. `_mec_server_error(url, body_text)` detects `Error.aspx`/`aspxerrorpath` in the URL and is checked in both `_search_cf12` (Phase D) and `download_independent_expenditures` (Phase E) before the bot-block check. Retried at most **once**, regardless of `max_tries` — unlike a WAF block, a fresh reload rarely fixes an application-level exception tied to a specific committee/year's underlying data, so burning the full retry budget wastes time. If it persists, the search returns `"blocked"` (not recorded as done) rather than `"empty"`, so a future re-run will retry it — but be aware some committee/years may simply always 500 on MEC's end and need to be accepted as permanently unreachable via this report.

**Postback-navigation race (Phase D and E).** Confirmed live in the page's own HTML: the `lbtnContr`/`lbtnExpend`/`lbtnAdvanced` tab-switch links and the Year `<select>` (`ddYear`) all trigger `__doPostBack` full-page postbacks. Critically, `ddYear`'s is wired via `onchange="javascript:setTimeout('__doPostBack(...ddYear...)', 0)"` — an **async**, zero-delay timer, not a synchronous call. A first fix attempt called `page.wait_for_load_state("load", timeout=30_000)` immediately after each postback-triggering action; this was *insufficient* for `ddYear` specifically and reproduced in production even after deploying it: since the postback hasn't actually started yet at the moment `wait_for_load_state` is called (the `setTimeout` hasn't fired), Playwright can see the page as "already loaded" from the *prior* page and return instantly — then the next action (`page.fill`) ends up racing the real navigation once the timer fires a moment later, producing `Page.fill: Timeout 30000ms exceeded ... waiting for navigation to finish... navigated to CF12_ContrExpend.aspx`. **Fixed properly** by wrapping each of the three postback-triggering actions (`click(main_tab_id)`, `click(lbtnAdvanced)`, `select_option(ddYear, ...)`) in `with page.expect_navigation(wait_until="load", timeout=30_000):` instead — this registers the navigation listener *before* performing the action, so it can't miss a navigation that starts late, unlike a wait called after the fact. Applied in both `_search_cf12` and `download_independent_expenditures`. Additionally, the entire per-attempt search sequence in both functions is wrapped in a single `try/except Exception` that feeds any unexpected failure back into the existing retry/backoff loop — previously only the popup-open (or download) step was guarded, so any other unhandled exception in the sequence would crash straight past the retry design and out to the Phase D/E loop's top-level `except Exception`, burning one of the circuit breaker's `MAX_CONSECUTIVE_ERRORS` budget instead of being retried in place. `except Exception` (not bare `except:`) is used throughout so `KeyboardInterrupt` still propagates.

**No result-set truncation on export (verified live).** MEC's on-screen results are paginated (~130 rows/page), which raised the question of whether large/active committees might need the search broken into sub-ranges (by contribution amount and/or date) to avoid an export cap. Tested directly against the Missouri Democratic State Committee (`C000960`), which has 478 contribution records for 2024 alone — a genuinely large single-committee/year result set. The "Export Results to Excel" button was confirmed (by downloading and counting rows) to export **all 478 rows**, not just the ~130 visible on the current on-screen page — export ignores the UI's pagination and dumps the full underlying data source, as is standard for ASP.NET GridView exports. No amount-range/date-range splitting is needed for correctness; the existing one-export-per-(committee, year) design already captures complete data even for the state's most active committees.

**Export-download retry (Phase D):** `download_transactions`'s final "click Export, wait for the download" step previously had no retry at all — confirmed live in production (`Timeout 120000ms exceeded while waiting for event "download"`) even after `_search_cf12` had already successfully found the results and Export button. Now retried up to 2 times on the same already-loaded popup (no need to redo the search) before giving up and returning `"blocked"`. `download_independent_expenditures`'s equivalent export-download step already had this retry from an earlier pass. **Also confirmed in production:** a blind retry can itself fail differently — `Page.click: Timeout 30000ms exceeded ... waiting for locator("#ContentPlaceHolder_btnExport")` — because the popup's DOM changed between attempts (navigated to a block/error page, or some other state change) and the button simply isn't there anymore. Before retrying, the code now checks whether the Export button still exists; if not, it inspects the popup for the `_mec_server_error`/`_looks_bot_blocked` signatures to log an accurate reason and bails immediately as `"blocked"` rather than burning the full click timeout on a retry that can't succeed.

**Physical clicks on tab/postback links are unreliable — use `__doPostBack()` directly.** Even after the `expect_navigation()` fix above, production still hit `Timeout 30000ms exceeded ... waiting for navigation until 'load'` on the very first tab click of a fresh page. Watching the actual automated browser window confirmed why: the click was landing on the page's embedded YouTube video ("Following Campaign Finance Money Series") near the top of the page instead of the intended tab link, so the link's own postback never fired at all — `expect_navigation()` was correctly waiting for a navigation that simply never started. Root cause is presumably a layout/hit-testing quirk from the iframe, not anything year/committee-specific. **Fixed by bypassing physical clicks entirely** for every `__doPostBack`-triggering control (`lbtnContr`/`lbtnExpend`, `lbtnAdvanced`, `ddYear`): `_postback(page, control_name)` and `_select_year_and_postback(page, select_id, year)` call the page's own `__doPostBack(eventTarget, eventArgument)` JS function directly via `page.evaluate()` — exactly what a successful click on the link already does under the hood (confirmed from the `href="javascript:__doPostBack(...)"` attributes themselves) — wrapped in `expect_navigation()` as before. This is immune to anything on-screen intercepting the click, since no physical click ever happens. `EVENT_TARGET_PREFIX = "ctl00$ctl00$ContentPlaceHolder$ContentPlaceHolder1$"` is the shared UniqueID prefix (confirmed from the page HTML) used to build each control's postback target name — note it uses `$` as the separator, unlike the client-side element ID prefix `P` (which uses `_`), so it's kept as a separate constant. `btnSearch` and `btnExport` are left as real clicks since they're genuine `<input type="submit">` buttons lower on the page, not `javascript:` postback links, and weren't implicated by this failure mode.

**MEC server-error page can land on the main tab, not just the popup.** The `_mec_server_error` check added earlier only ran after a popup had successfully opened. Confirmed live in production that this misses a real case: when the server-error bug fires on the `btnSearch` submission itself, the results page's `onload` handler — which is what normally calls `window.open()` to show the results popup — never runs at all, because the response is the entirely different `Error.aspx` template rather than a page carrying that script. The browser just navigates the *main* tab to the error in place; no popup ever opens. That landed in the generic `except Exception` fallback (a 25s `context.expect_page()` timeout, retried up to the full slow `max_tries` budget with growing backoff) instead of the fast "retry once, then give up" path meant for this exact bug — which is what produced the "stuck on the error page for a long time" experience in production. Fixed by also checking the main page's own URL/body for the `_mec_server_error` signature inside that generic exception handler, before falling back to the slow multi-attempt retry.

**`expect_navigation()` doesn't reliably detect same-URL postback navigations.** Even after switching from physical clicks to direct `__doPostBack()` JS calls (above), production still hit `Timeout 30000ms exceeded ... waiting for navigation until 'load'` — despite the postback apparently firing correctly (confirmed: the error page itself, when this happened on a genuine MEC server error, showed the postback's *result*, not a stalled form). The postbacks on this page are same-URL POST submissions (the URL never changes across the whole multi-step search), which is a known weak spot for Playwright's `expect_navigation()`/navigation-event detection — it's built around frame-lifecycle/URL heuristics that don't reliably fire for every same-URL full-page POST. **Fixed by abandoning Playwright's navigation detection entirely** for these postbacks: `_wait_for_postback(page, trigger)` now polls the page's `__VIEWSTATE` hidden field (via `page.wait_for_function`) for its value to change, since ASP.NET regenerates `__VIEWSTATE` on every successful postback. This is a robust, actual-site-behavior-based signal that doesn't depend on Playwright correctly classifying the underlying navigation at all. `_postback()` and `_select_year_and_postback()` both delegate to this helper now instead of wrapping their JS-triggered postback in `expect_navigation()`.

**Export-download timeout shortened from 120s to 45s (Phase D and E).** With all the fixes above in place, a committee/year that's permanently broken on MEC's end (like A101029/2026, which hits `_mec_server_error` reliably) still cost up to ~2 minutes *per relation type* (~4 minutes total for one committee) before giving up, because the download-wait timeout was 120 seconds and the retry loop tries twice. Since real exports — including a large committee's several-hundred-row file — were confirmed live to complete quickly, there's no reason to wait 120s for one that was never coming. Shortened to 45s in both `download_transactions` and `download_independent_expenditures`, cutting the worst case for a single broken committee/year roughly in half without risking legitimate slow-but-real downloads.

**Redundant `lbtnContr` postback caused a guaranteed 30s hang on every Contributions search.** `lbtnContr` ("Contributor") is the page's already-active default tab on a fresh `CF12_URL` load — confirmed against the page's own HTML, walked step by step: Advanced Search tab, the Contributor Name radio buttons, the Year dropdown/date-range/amount/Committee ID fields all matched what the code already does, but the very first step (`_postback(page, main_tab_id)` fired unconditionally for both `lbtnContr` and `lbtnExpend`) didn't. Re-sending `lbtnContr`'s `__doPostBack` when it's already the active tab is a no-op on the server, and a no-op postback doesn't regenerate `__VIEWSTATE` — so `_wait_for_postback`'s VIEWSTATE-diff poll sat for the *entire* 30s timeout waiting for a change that was never coming, on every single Contributions search, before falling into the generic exception/retry path. This explains why Contributions (always processed first for every MECID) was consistently the worse-behaved relation type compared to Expenditures (a genuine tab switch, which does regenerate `__VIEWSTATE` normally). **Fixed** by only sending the main-tab postback when actually switching tabs — i.e. skipped entirely when `main_tab_id == "lbtnContr"` — leaving `lbtnAdvanced`'s postback and everything after it unchanged.

**Export-download timeout shortened again, 45s → 10s, plus fast diagnosis and reload-retry on the export click itself (Phase D and E).** After the `lbtnContr` fix above, a full production run revealed the export-download failure was actually the dominant failure mode across *many different* committees, not just A101029 — most committee/years hit "export download failed (Timeout 45000ms...)" then "MEC server error appeared mid-download" on both contributions and expenditures. Root cause: `download_transactions` always waited out the *entire* 45s download timeout before doing any diagnosis, even though the failure (an error/bot page instead of a file) is knowable almost instantly by just checking the popup's current URL/text. Confirmed live, repeatedly: a failed export **never** eventually arrives no matter how long you wait — it's binary, not slow-but-real. Rewrote the export step to: (1) use a much shorter `EXPORT_DOWNLOAD_TIMEOUT_MS` (10s) for the download wait itself; (2) on a miss, immediately check the popup for `_mec_server_error` — if that's what happened, give up right away (confirmed not to be a reloadable/transient condition — a fresh reload of the same committee/year reproduces the identical MEC-side exception), instead of retrying; (3) separately check for a `_looks_bot_blocked` interstitial — which, unlike the MEC server error, IS the transient kind that clears on a fresh attempt, so this now gets its own reload-and-retry (up to `MAX_EXPORT_BOT_RETRIES` = 3), redoing the *whole* search via `_search_cf12` to get a brand-new popup rather than re-clicking Export on a popup that's now showing the block page — the same "reload and try again" treatment Phase B's committee-detail sweep already gets, previously missing from this specific step; (4) only if neither signature matches (a genuinely dropped/slow download) does it fall back to the old same-popup click-retry. `download_independent_expenditures` (Phase E) gets the same shortened `EXPORT_DOWNLOAD_TIMEOUT_MS`; it didn't need the same restructuring since its retry loop already reloads the whole search from scratch on any export failure.

**Committee A101029 "cold start" pattern — superseded.** Across repeated debug restarts, MECID `A101029` (a small municipal-judge candidate committee, alphabetically early — always the first item swept) failed differently nearly every time: server error, download timeout, missing button, navigation race. This was originally attributed to a browser "cold start" cost compounding because a `"blocked"` result is never written to the manifest, so every restart re-hit the same first MECID. With the `lbtnContr` no-op-postback bug fixed above, the far more likely explanation is that A101029's contributions search was hitting the guaranteed 30s VIEWSTATE-poll hang described above on *every* restart — which, combined with retries and the export-download timeout, produced exactly the "different failure mode every time" pattern (the specific error varied depending on exactly when/where the 30s+ cumulative delay pushed a subsequent step past its own timeout). Left here for the record; if A101029 (or any other committee) still shows anomalous behavior after this fix, the cold-start theory should be revisited.

**Initial-run CAPTCHA — needs a one-time human solve, then persists via a saved browser profile.** Confirmed directly by the user: the very first navigation of a scrape occasionally hits an actual interactive CAPTCHA (distinct from the plain "Request Rejected" text `_goto_with_retry` already auto-clears with a reload+sleep) — and confirmed a reload does **not** get past this one; it genuinely requires a human to solve it. Root cause: the scraper previously launched a fresh `browser.new_context()` on every run, which starts with zero cookies every time, so MEC's Incapsula WAF has no way to recognize a returning, already-trusted session — a fresh challenge was effectively guaranteed on every single invocation, not just a true "first ever" run. **Fixed** by switching to `p.chromium.launch_persistent_context(PROFILE_DIR, ...)` (`PROFILE_DIR = .playwright-profiles/missouri/`, outside `data/Missouri/raw` so parsers' `.xls` globbing never sees Chrome profile internals) — cookies, including whatever trust/session cookie Incapsula sets after a challenge is solved, now persist to disk across runs. Solve the CAPTCHA by hand once against this profile and later runs reuse those cookies, skipping the challenge entirely as long as the trust cookie hasn't expired or been invalidated by MEC's WAF — if it ever reappears, that's the signal to solve it once more, not a code regression. Not yet independently confirmed end-to-end (i.e. that a second run after solving once actually skips the challenge) — worth the user watching the browser window on the next couple of runs to confirm.

**Expected runtime:** Phase A and E are each under a few minutes. Phase B (full committee-detail sweep) is several hours for ~13,000 committees at ~0.15s/request. Phase D scales with `(# committees) × (# years) × 2` — a single current-year incremental run across all ~13,000 committees is still many thousands of searches; a multi-year historical backfill should be expected to run for many hours to multiple days and should be run unattended, relying on the manifest for resumability.

## Parser

`src/pipeline/parsers/missouri.py`

**person_id model:** `person` — see the Election History finding above. A Missouri candidate committee's MECID is not re-issued per cycle or per office, so `state_filer_id` is already a stable person-level key; `person_id` is derived from it directly (no name/office/district grouping needed, unlike the `committee` model used by states such as Alabama/Arizona/California).

**Output tables:** `committees.csv`, `candidates.csv`, `contributions.csv`, `expenditures.csv`, `loans_debts.csv` (empty — no structured loan/debt export found on the MEC site).

**Key transformations:**
- `committees.csv` is sourced from `committee_detail.csv` (Phase B) when available; falls back to the bulk `committees_active.xls`/`committees_terminated.xls` exports (no party/address/treasurer) if the detail sweep hasn't been run yet.
- `candidates.csv` is built from `election_history.csv` — one row per (committee, election) — joined to `committee_detail.csv` by MECID for `candidate_name`/`party`. Rows for committees with no `candidate_name` (i.e. PACs, which never populate the Election History grid anyway) are skipped.
- `candidate_first`/`candidate_last` are a naive first/last-token split of `candidate_name` — MEC exposes only a single combined name field.
- Amounts stripped of `$`/commas; dates normalized `MM/DD/YYYY` → `YYYY-MM-DD`.
- `contributor_name`/`contributor_type` are synthesized (MEC has no single contributor-type field): the `Committee.1` transfer flag → "Committee", else `Contributor-Company` present → "Business", else `Contributor-First/Last Name` → "Individual".
- `amended` is inferred from the literal substring "AMENDED" in the free-text `Report` field — MEC has no dedicated amended flag on this export.
- `filing_id` is populated with the free-text `Report` name rather than a numeric ID — MEC doesn't expose one on these exports.
- **Independent expenditures are folded into `expenditures.csv.gz`**, not a separate output file. Each `independent_expenditures_{year}.xls` row becomes an expenditures row with `transaction_type="Independent Expenditure"`, `committee_name` = the spending committee (`Reporting Committee`), `affiliated_candidate_name` = the targeted candidate (parsed out of the combined `Candidates Name and Address` field via `split_candidate_name_address()`), `support_oppose` = `"S"`/`"O"` from `Support/Oppose`, `office` = `Office Sought`, and `payee_name`/`purpose` left blank since MEC doesn't disclose a vendor on this particular report. `candidate_name` is deliberately left blank on these rows — see the `candidate_name` vs `affiliated_candidate_name` distinction in `columns.py`: an independent-expenditure committee spending against a candidate is never that candidate's own committee.

**Limitations:**
- `office`/`election_year` on contributions/expenditures are left blank/set to the search year respectively — MEC's per-transaction records don't indicate which specific election a transaction relates to, only which committee/year it was filed under. (Independent-expenditure rows are the exception: `office` is populated from `Office Sought`.)
- `affiliated_candidate_name`/`support_oppose` on **committees.csv** (which PAC a committee supports, as a standing affiliation) are left blank — no structured source for this was found; would require a hand-reviewed `src/registries/committees/missouri.csv` fallback like other states use for the same gap. This is distinct from the same-named columns on **expenditures.csv**, which independent-expenditure rows do populate per-transaction (see above).
- Expenditure `category` is left blank on all rows, including independent expenditures — MEC's expenditure exports have no category field distinct from the free-text `Purpose`/the report type itself; the "Paid"/"Incurred" `Expenditure Type` and (for IE rows) the literal `"Independent Expenditure"` are used as `transaction_type` instead, both mapped to canonical values (`Monetary`, `Independent Expenditure` respectively) in `expenditure_categories.csv`.
- **`Candidates Name and Address` name/address split is best-effort.** MEC concatenates the candidate's name and full address into one string with no reliable delimiter. `split_candidate_name_address()` splits at the first street-start marker (a digit run, or a P.O. Box marker), falling back to stripping a trailing "City ST ZIP" chunk. Confirmed correct against live samples (`"Friends of Charlie Herbst Seabaugh P. O. Box 41   Jackson MO 63755"` → `"Friends of Charlie Herbst Seabaugh"`), but a candidate name containing a digit, or a street address with no leading number, will split wrong.
- **No MECID for the reporting committee on independent-expenditure rows.** MEC renders `Reporting Committee` as a postback link (`javascript:__doPostBack(...)`) in the live UI, not a plain URL with the MECID embedded, and the exported HTML carries only the plain committee name — so these rows can't be joined to `committee_detail.csv` by MECID, only by name.

## Data Notes

- **Statewide bulk transaction search exists after all — a committee-scoped search is not required.** Originally documented as "no bulk transaction export... every record requires a committee-scoped search" based on a test that only tried Year alone; a Year + date range (Committee ID left blank) genuinely works statewide. See "Phase D was rearchitected" above for the full story, including the real root cause of most export failures (a same-URL HTTP 503, not a size/committee-specific issue).
- **Party lives only on the committee detail page**, not in the bulk committee list — a full `--entities` sweep (Phase B) is required before `party` is populated for any candidate.
- **Committee IDs are durable person identifiers for candidates** — confirmed on a sitting governor's committee, which kept the same MECID across three different offices over four election cycles. Don't assume a new MECID implies a new person, or that a stable MECID implies a single office/cycle — check `election_history.csv`.
- **Duplicate "Committee" header in the raw contribution export** — see Raw Data Structure above; handled via `_dedupe_headers`, but a reason to be cautious if ever re-parsing these files with a different tool that doesn't replicate `pandas.read_html`'s dedup convention.
- **Popup blocker gotcha is environment-specific** — this only manifests because MEC's results open via a delayed `window.open()`, not because of anything unusual about Playwright. Any future scraper work against this site (e.g. exploring the unimplemented "Committee to Committee" search tab) should launch with `--disable-popup-blocking` from the start rather than rediscovering this.
- **"Committee to Committee" search tab is unexplored** — `CF12_ContrExpend.aspx` has a third tab for committee-to-committee transfers that wasn't investigated. The `Contributor-Committee`/`Committee.1` transfer flag on the contribution export already captures transfers *received*, so this may be redundant, but transfers *made* (which would otherwise only show up as generic expenditures) aren't separately verified as covered.
- **Stale-scroll gotcha during interactive testing** — not a code issue, but worth recording: MEC resets scroll position to the top after every ASP.NET postback, which caused several misclicks during manual exploration of this site (clicking cached coordinates from before a postback). Not applicable to the scraper itself, which uses element IDs rather than coordinates.
- **Independent expenditures were a separate, initially-missed data source.** The original scraper only covered Phase D's per-committee "Expenditure" tab (a committee's own ordinary spending) — it did not cover `CF_SearchDirExp.aspx`'s "Committee Expenditures for Candidates" search, which is MEC's actual independent-expenditure report (committee spending FOR/AGAINST a candidate). Added as Phase E. Confirmed live: 1,718 records for report year 2026 alone, none of which were previously captured.
- **Non-committee expenditure reports are a known, deliberately unimplemented gap.** MEC has a separate "Non-Committee Expenditures" search (`CF14_nonCommExp.aspx`) for individuals/businesses/groups (not registered committees) spending $500+ to support/oppose a candidate or ballot measure. These are filed on paper and scanned — confirmed live that the scanned PDFs carry an embedded OCR text layer (`/Producer (Tesseract 3.04.02)`), so full binary-image OCR isn't needed, but the extracted text is noisy (old Tesseract version, unstructured table layout) and would need dedicated regex-based field parsing with real error/missing-data rates to turn into structured rows — deferred for now. The DMS document endpoint these PDFs are served from (`mec.mo.gov/DMS/DOC/V/{id}`) sits behind the same WAF as the rest of the site, so this too can only be scraped from a local machine.
- **`CF12_BallotSearch.aspx` ("Committee Expenditure for Ballot Measures Search") is the ballot-measure analog of Phase E** — independent expenditures for/against ballot measures rather than candidates. Out of scope for this candidate/committee-focused pipeline; noted here in case ballot-measure coverage is ever added.
